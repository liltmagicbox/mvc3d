# 03. 데이터 모델 — 무엇을 어디에 실어 보내나

**결론: 세 평면으로 분리하고, 평면 사이는 노드 포함관계가 아니라 id로 잇는다.**
점수·이름 같은 게임 데이터를 공간 노드에 넣지 않는다.

| 평면 | 내용 | 운반 | 빈도 |
|---|---|---|---|
| 자산 (정적) | 지오메트리, 머티리얼, 스킨(조인트 트리), 애니 클립 | glTF(.glb), SCHEMA가 kind→자산 매핑 | 접속 시 1회 |
| 상태 (핫) | 변환, 포즈, "그려지는" per-instance 수치(HP바 등) | STATE 섹션 (§02) | 매 프레임 |
| 게임 (콜드) | 점수, 이름, 인벤토리, 스폰/사망 | EVENT JSON | 바뀔 때만 |

판별 기준 한 줄: **매 프레임 그려지는 수치면 STATE 섹션, 아니면 EVENT.**

## 가이드

- glTF 연결: SCHEMA로 `{ "kinds": { "65537": {"glb":"soldier.glb","mesh":0,"skin":0} } }`
  → 뷰어가 .glb 로드해 VAO 구성, 이후엔 섹션 배열만 흘려받는다.
- 점수: 바뀔 때 `ctx.emit({'type':'score','player':'p1','value':1200})` →
  뷰가 `{player_id: score}` dict 캐시 → HUD가 캐시를 읽는다. 재전송 없음.
- 머리 위 이름표/HP바: 앵커(위치)는 이미 STATE에 있는 그 유닛의 transform,
  내용(이름)은 캐시에서. HP 채움값처럼 매 프레임 그려지는 수치는
  `(KIND_HP, hp_f32)` 섹션 하나 추가 (N×1 f32 = 4KB@1000).

## 스켈레탈

| 옵션 | 와이어 | 크기/캐릭터(128조인트) | 언제 |
|---|---|---|---|
| (a) 조인트 팔레트 | mat4×n_joints (comps=16) | 8KB | 래그돌, 절차적 포즈 |
| (b) pos+quat/조인트 | comps=7~8, f16 가능 | 1.8~3.6KB | (a)의 압축판 |
| (c) 애니 상태만 | clip id + t + blend | **~16B** | 기본 권장 |

(c)가 핵심: 게임플레이가 포즈에 의존하지 않으면 시뮬은 포즈를 계산할 필요도
없다. 뷰어가 glTF 애니메이션을 직접 샘플링한다. 히트박스 등 필요할 때만
(a)/(b)로 폴백. 셋 다 섹션 포맷("섹션=배치")에 그대로 들어간다.

## id 정렬 (인스턴스 배열 ↔ 게임 데이터 매칭)

인스턴스 배열은 순서 기반이라 행↔entity 연결고리가 필요하다:

1. **UnitArray 인덱스 재사용** (axis3d에 이미 있음): acquire/release 슬롯이
   안정적이면 "kind 내 row 번호 = id". 생성/소멸만 EVENT로 알림.
2. **IDS 섹션**: `(KIND_IDS, ids_u32)` 섹션 추가 (N×u32 = 4KB@1000),
   pos 섹션과 행 정렬. 유닛이 자주 죽고 재활용되면 이쪽이 안전.

## 함정

- glTF `extras`에 게임 데이터를 넣는 게 정당한 경우는 **파일로 저장할 때뿐**
  (세이브/에디터/리플레이). 런타임 와이어에는 안 태운다.
- EVENT는 '사건'이라 드랍되면 소실 — 신뢰 채널로 보낸다 (§04).
